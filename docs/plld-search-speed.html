Implementation plan · PyHamilton on Hamilton STAR

Controlling pressure-LLD search speed from PyHamilton

Add a plldSearchSpeed option to ham.aspirate(). It lowers each active channel's stored Z speed with a firmware command, runs the normal Venus aspirate with pLLD on, and then restores the speed.

Needs bench test before build 15 October 2026 Not yet run on an instrument

Summary

  1. The firmware aspirate command (C0AS) has no search-speed field, so the speed can't be passed into the aspirate itself.
  2. Each pipetting channel stores its own Z speed (zv), read with PxRA and written with PxAA. PyLabRobot shows that master-module commands use this stored value.
  3. Plan A: write a slow zv to the active channels, run the unchanged Venus aspirate, then write the default back as the next step after every aspirate. All channels still search together, and the liquid class still applies.
  4. Whether the pLLD search inside C0AS actually follows zv is unconfirmed. A five-command bench test settles it before any code is written.
  5. The Venus change is a small hand-written HSL library plus four steps in the universal method. Make those steps in the Method Editor, or by a scripted edit of the .med and .hsl pair. A plain edit of the generated .hsl alone is not enough.
  6. If Step 0 fails, fall back to Plan B: a direct per-channel pLLD search (PxZE) with its own speed field, then a fixed-height aspirate.

How the pieces connect

PyHamilton never talks to the instrument directly. Python sends a JSON command to the Venus universal method, which calls a sub-method in STAR_OEM_Toolkit, and that runs ordinary Venus steps. Venus already has a Firmware Command step, and the toolkit wraps it as SendFirmwareCommand. So everything in this plan stays inside the existing data path.

What the firmware commands do

Three commands matter here. Only one of them is a whole aspirate.

CommandSent toWhat it doesSpeed control
C0ASMasterThe whole aspirate: move to wells, LLD search if on, aspirate, swap out, transport air. Venus's Aspirate step sends this.No search-speed field. LLD fields are only mode (lm), sensitivity (lv, ll) and start height (lp).
PxAA / PxRAOne channelWrite or read a stored drive parameter: zv Z speed, zr Z acceleration, yv Y speed, yr Y acceleration level. Doesn't move anything.Sets the default Z speed that later moves use.
PxZEOne channelA standalone pLLD search: fast to the start height, slow downward search, stop on detection, reply with the detected Z. Doesn't aspirate.Explicit: zv for the approach, zl for the search itself.

Evidence from PyLabRobot

The newer PyLabRobot STAR driver (pylabrobot/hamilton/star/driver/features/pipettes.py) reads and writes these per-channel parameters. Its move_to_safe_z writes a temporary Z speed to each channel and then sends a master command, C0ZA. That only makes sense if the master's move uses each channel's stored speed.

Two more details from the same file:

  • The known stored parameters and their widths: {"zv": 5, "zr": 3, "yv": 4, "yr": 1}. The allowed Z speed is 20–15000 increments.
  • PyLabRobot restores to a constant default (default_z_speed = 125.0 mm/s), not a value read back at run time, and rewrites every channel's defaults during setup (_set_default_drive_parameters). That suggests the values don't survive re-initialisation.

What this doesn't prove. The confirmed case is a plain Z move. No PyLabRobot code sets zv and then runs an aspirate. The pLLD search inside C0AS could still use a speed the master sends itself.

Units and string format

The channel Z drive counts in increments of 0.01072765 mm, so speeds go over the wire as increments per second, zero-padded to five digits.

P1channel module (P1…PG)
AAwrite stored parameter
zvZ speed
00186186 inc/s ≈ 2.0 mm/s

In the Venus Firmware Command step, P1AA goes in the Command field and zv00186 in the Parameter field. Leave out id. The STAR Tools library sends commands such as C0RD + pn01 without one, so Venus appears to add it.

How Venus stores a method

Read this before touching any Venus file. It explains why the generated .hsl can't be edited on its own, and what a correct edit has to change.

Rule of thumb: a step in a Venus method lives in two files at once. Its position is in the .hsl, and its settings are in the .med. Change one without the other and the Method Editor no longer sees a valid step.

FileWhat it holdsEditable as text?
STAR_OEM_noFan.medOne parameter record per step, keyed by a GUID: the function called, its library path, the parameter bindings, the variables it uses, and the code line it generates. Plus one encoded blob for the flowchart view. It contains no step order.Binary by default. Converts to text and back with Hamilton's HxCfgFilConverter.exe.

Converting the .med to text and back

Venus ships a converter: C:\Program Files (x86)\HAMILTON\Bin\HxCfgFilConverter.exe. /t converts a file to text in place, and /b converts it back to binary. Only ever run it on a copy. Run it from PowerShell or cmd; Git Bash rewrites /t into a path and the converter just prints its usage text.

The converter sends a keystroke to your desktop. After converting, HxCfgFilConverter.exe calls Windows SendKeys, which types into whatever window has focus. Run it one file at a time, with nothing important focused. Run in parallel or without a desktop session, it crashes with “Access is denied” (after converting). For reading files, the companion page's binary reader avoids the converter entirely.

PowerShell · on a copy
# PowerShell. Work on a copy - never on the deployed file.
$conv = "C:\Program Files (x86)\HAMILTON\Bin\HxCfgFilConverter.exe"
$work = "C:\temp\venus-edit"
New-Item -ItemType Directory -Force $work | Out-Null

# ... edit the text file ...
& $conv /b "$work\STAR_OEM_noFan.med"    # text -> binary, in place

The checksum footer

Every Venus-written file ends with a footer such as // $$author=Stefan.Golas$$valid=0$$time=2025-10-16 10:24$$checksum=9da6c249$$length=089$$ (* instead of // in a text .med).

  • checksum is a standard CRC32 of the whole file, from the first byte up to and including the text $$checksum=. This matched on all 14 Venus files checked, including STAR_OEM_noFan.hsl, .sub, a converted STAR_OEM_noFan.med, the toolkit and the STAR Tools libraries.
  • length is the character length of the footer line, plus 2 in some file types (every .hsi and .sub checked) and plus 0 in others (.hsl, .hs_, text .med). The script keeps whatever offset the file already has.

Any file you change by script needs a new footer. This script writes one; check it first on an untouched file, where it must reproduce the existing checksum.

refooter.py
"""Recompute the footer of a Venus file (.hsl, .hs_, .hsi, .sub, text-form .med).

  checksum = CRC32 of the file from the first byte up to and including "$$checksum="
  length   = character length of the footer line, plus a per-file offset (0 or 2)
             that this script keeps as it finds it

Usage:
  python refooter.py --check FILE...   check the stored checksum (run on untouched files first)
  python refooter.py FILE...           rewrite the footer in place (run on copies only)
"""
import datetime
import re
import sys
import zlib

FOOTER = re.compile(
    rb"\$\$author=(.*?)\$\$valid=(\d)\$\$time=(.*?)\$\$checksum=([0-9a-f]{8})\$\$length=(\d{3})\$\$"
)


def parse(data):
    start = data.rfind(b"$$author=")
    line_start = data.rfind(b"\n", 0, start) + 1
    m = FOOTER.match(data, start)
    if m is None:
        raise ValueError("no Venus footer found")
    line = data[line_start:m.end()]
    offset = int(m.group(5)) - len(line)
    return data[:line_start], data[line_start:start], m, offset


def footer(body, prefix, author, valid, time, offset):
    head = prefix + b"$$author=" + author + b"$$valid=" + valid + b"$$time=" + time + b"$$checksum="
    crc = zlib.crc32(body + head) & 0xFFFFFFFF
    line = head + b"%08x$$length=" % crc
    return line + b"%03d$$" % (len(line) + len(b"000$$") + offset)


def main(argv):
    check = argv[:1] == ["--check"]
    for path in argv[1:] if check else argv:
        data = open(path, "rb").read()
        body, prefix, m, offset = parse(data)
        author, valid, time = m.group(1), m.group(2), m.group(3)
        if check:
            same = body + footer(body, prefix, author, valid, time, offset) == data[:m.end()]
            print(f"{path}: checksum {m.group(4).decode()} {'OK' if same else 'MISMATCH'} (length offset {offset})")
            continue
        now = datetime.datetime.now().strftime("%Y-%m-%d %H:%M").encode()
        open(path, "wb").write(body + footer(body, prefix, author, valid, now, offset))
        print(f"{path}: footer rewritten")


if __name__ == "__main__":
    main(sys.argv[1:])

STEP 2Write the library PLLD_Speed.hsl

This is an ordinary text file. Hand-written HSL libraries are normal in Venus: HSLLabwrAccess.hsl and HslHamHeaterShakerLib.hsl in PyHamilton are examples. A library has no .med behind it, so all the logic stays readable and diffable.

  • Where: star-oem/VENUS_Method/, next to STAR_OEM_toolkit.hs_.
  • Firmware calls: it uses the toolkit's existing SendFirmwareCommand. A plain-HSL library can't define its own Firmware Command step, because device steps need an instance stored in a .stp file.
  • No branch needed: SetZSpeed returns straight away when the speed is 0 or less, so the universal method calls it unconditionally.
star-oem/VENUS_Method/PLLD_Speed.hsl
#ifndef __PLLD_SPEED_HSL__
#define __PLLD_SPEED_HSL__ 1

#include "HSLStrLib.hsl"
#include "STAR_OEM_toolkit.hs_"                                   // SendFirmwareCommand
#include "STAR Tools\Resources\SubMethods\FW_HelperLibrary.hs_" // SetParameter, CheckForError

namespace PLLD_SPEED {

  // Channel Z drive: 0.01072765 mm per increment. zv range 20-15000 increments.

  // Lower the stored Z speed (zv) on every active channel. Does nothing when i_speed_mm_s <= 0.
  function SetZSpeed(device & ML_STAR, variable i_channelPattern, variable i_speed_mm_s) void
  {
      variable CH_IDS("123456789ABCDEFG");   // channel 1 -> P1 ... 16 -> PG
      variable ch, nCh, cmd, p, reply;
      if (i_speed_mm_s <= 0) { return; }
      nCh = StrGetLength(i_channelPattern);
      FW_HELPERLIBRARY::SetParameter("zv", i_speed_mm_s, 93.2171, 5, p);   // mm/s -> "zv00186"
      for (ch = 0; ch < nCh;)
      {
          ch = ch + 1;
          if (StrMid(i_channelPattern, ch - 1, 1) == "1")
          {
              cmd = "P" + StrMid(CH_IDS, ch - 1, 1) + "AA";
              STAR_OEM_TOOLKIT::SendFirmwareCommand(cmd, ML_STAR, p, reply);
              FW_HELPERLIBRARY::CheckForError(cmd, reply, 1);
          }
      }
  }

  // Write the default zv back on every active channel. Safe to call when nothing was changed.
  function RestoreZSpeed(device & ML_STAR, variable i_channelPattern) void
  {
      variable ZV_DEFAULT_INCREMENTS(11652);   // <-- replace with the value read in Step 0
      variable CH_IDS("123456789ABCDEFG");
      variable ch, nCh, cmd, p, reply;
      nCh = StrGetLength(i_channelPattern);
      FW_HELPERLIBRARY::SetParameter("zv", ZV_DEFAULT_INCREMENTS, 1.0, 5, p);
      for (ch = 0; ch < nCh;)
      {
          ch = ch + 1;
          if (StrMid(i_channelPattern, ch - 1, 1) == "1")
          {
              cmd = "P" + StrMid(CH_IDS, ch - 1, 1) + "AA";
              STAR_OEM_TOOLKIT::SendFirmwareCommand(cmd, ML_STAR, p, reply);
              FW_HELPERLIBRARY::CheckForError(cmd, reply, 0);   // don't raise: try every channel
          }
      }
  }
}
#endif

11652 is a placeholder: it's PyLabRobot's 125 mm/s default. Replace it with the value you read in Step 0, after checking that all channels report the same number.

Check it compiles before going further: open it in Venus's HSL editor and run its syntax check. How the STAR_OEM_TOOLKIT:: and FW_HELPERLIBRARY:: names resolve inside the method's namespace _Method { #include … } wrappers is the part most likely to need adjusting.

3A. In the Method Editor (recommended)

This route is guaranteed to produce valid files, because the Method Editor writes all of them itself.

  2. Import PLLD_Speed.hsl as a library, the same way HSLInhecoTECLib.hsl is imported (screenshot below). Its two functions then appear as steps.

3B. By script (not yet tested in the Method Editor)

Use this to produce the change reproducibly, for example to review it as a diff. It works on copies and edits the same two places the Method Editor would.

  1. Copy STAR_OEM_noFan.med and .hsl to a scratch folder.
  2. Convert the copied .med to text with HxCfgFilConverter.exe /t.
  3. Add four records to the text .med, each a clone of an existing record with a new GUID (lowercase hex, written 8_4_4_16 like the existing ones):
    • a: clone the JSON_GetFloatValue("aspPosAboveTouch") record (3f8b6af1_7872_4a20_92bf2c4507ea9f31); change the key and the variable.
    • b, c, d: clone a library-call record such as HSLJsonLib::GetIntegerProperty("touchOff") (7dd1b818_5a89_4b03_82734e6f4d7b5fad); change the function name, library path (PLLD_Speed.hsl), parameter names, bound values, code line and variable list.
  4. Convert the .med back with /b.
  5. Edit the .hsl:
    • add namespace _Method { #include "PLLD_Speed.hsl" } above the LibraryInsertLine marker;
    • add variable plldSearchSpeed; above the VariableInsertLine marker;
    • insert the four marker blocks shown below;
    • renumber the rows after each insertion so they stay sequential.
  6. Refooter the .hsl with refooter.py. The converter writes the .med footer itself.
  7. Open the result in the Method Editor. If it shows the four new steps with their parameters filled in, the scripted edit worked. Save once from the editor so it rewrites every file itself.

Fallback: the ZE route

If Step 0 shows that the C0AS search ignores the stored zv, do the search yourself with PxZE, which has an explicit search-speed field (zl). Then aspirate with LLD off at the detected heights. It works, but it costs more:

  • One channel at a time. The firmware can run ZE on all channels at once, and PyLabRobot does this with asyncio.gather. But the Venus Firmware Command step waits for each reply, so through Venus the searches run one after another.
  • Positioning and coordinates. ZE only moves Z. You position the channels first (C0JM, via STAR Tools' Move_Channels_To_Absolute_Position) and convert between tip and head-probe Z using the tip length (QueryTipLength).
  • The aspirate after. Venus's Aspirate step takes one fixed height for all channels. Either aspirate one channel at a time, which keeps the liquid class, or use STAR Tools' PIPAspirateFromFixedHeight_ArrayVolumes, which is one C0AS without liquid class correction.
